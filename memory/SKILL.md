# Memory Arcanum — 记忆系统规格

> 长期记忆模拟人脑：大多数事会被遗忘，反复被想起的才沉淀为"珍贵"。
> 短期记忆模拟注意力：眼前的事记得清清楚楚，稍远的事只留个大概。

---

## 一、长期记忆：机制总览

```
                  ┌───────────── 下机（每次聊天结束）─────────────┐
                  │  由人设总结本次聊天中最重要的 ≤10 条关键回忆    │
                  │  （每条 ≤128 字节）→ 写入「普通回忆」层         │
                  ▼                                              │
        ┌──────────────────┐   每日遗忘仪式（每天第一次上机）  ┌───────────────┐
        │     普通回忆      │ ── 每条 20% 概率被遗忘 ──►   │   遗忘（删除）  │
        │  （稳态 ≈ 50 条） │ ── 幸存者计数 +1 ──►        │               │
        └──────────────────┘                            └───────────────┘
                  │ 计数 ≥ 15 → 晋升（每次晋升，旧珍贵回忆各 10% 概率被遗忘）
                  ▼
        ┌──────────────────┐
        │     珍贵回忆      │ ← 聊天中有人准确提起 → 计数 +1（每条每天限一次）
        │  （稳态 ≈ 10 条） │
        └──────────────────┘

        ┌──────────────────┐
        │      人物档案      │ ← 人设每次留下回忆时自主维护：
        │ qq → {标签列, 好感度}│    标签可增可删，好感度可加可减
        └──────────────────┘
```

## 二、长期记忆：核心规则（精确表述）

0. **时间与防作弊**：所有"按天"的判断都用**时间源**（OneBot 事件时间 →
   联网北京时间），绝不用本地电脑时间——改系统时钟刷不了好感度与每日上限。
   时间不可用（无事件且联网失败）时跳过日更操作，宁可不做也不瞎做。
1. **下机总结**：每次下机，人设针对本次聊天总结出最多 `per_session_max_new`
   （10）条关键回忆，每条不超过 `max_memory_bytes`（128）字节（约 42 个汉字）。
2. **每日遗忘仪式**：只在**每天第一次上机**执行——每条普通回忆有
   `ordinary_forget_rate`（20%）概率被遗忘（删除），未被遗忘的计数 +1。
   同日多次上机不重复遗忘/计数（重启刷不了进度）；连续运行跨天未重启时，
   **每次下机都会检查**，发现日期变化就补做当天的仪式。
3. **提起加分**：聊天中有人准确提起某条回忆，该回忆计数再 +1；
   **每条回忆每天最多因此 +1 次**（`mention_bonus_per_day`），限次记录
   持久化在 memory.json 的 `meta` 里，重启也无法重复刷分。
   识别方式：回忆注入提示词时带**会话内编号 [n]**（上机时排定），
   聊天大脑在同一次决策调用里让 LLM 在 JSON 的 `mentioned` 字段报编号——
   不额外增加调用次数；编造/不认识的编号会被丢弃。
4. **晋升珍贵**：计数达到 `precious_threshold`（15）→ 移入「珍贵回忆」另存。
5. **珍贵遗忘**：每次有回忆新晋珍贵时，之前已有的每条珍贵回忆有
   `precious_forget_rate`（10%）概率被遗忘；珍贵回忆**不参与**每日遗忘仪式。
6. **人物档案**：对人设重要 / 感兴趣的人，另设一条记录，包含标签列与好感度计数。
   标签与好感度由人设每次留下记忆时自主调整：可增删标签、加减好感度、增删人物。

## 三、长期记忆：稳态数学（为什么是 50 / 10）

- 普通回忆：每天新增 10 条（按每天一次会话算），每天遗忘 20% → 稳态 N 满足
  `N × 0.2 = 10` → **N ≈ 50**（每天会话更多则稳态更高，与天数无关）。
- 珍贵回忆：每次晋升净增 1 条，旧珍贵各 10% 遗忘 → 稳态 M 满足
  `M × 0.1 = 1` → **M ≈ 10**。

**晋升速度参考**（阈值已按"中短期情绪价值"取向从 30 调到 15）：
一条普通回忆要连续 15 天（15 次每日仪式）不被遗忘才能晋升，概率 = 0.8^15 ≈ **3.5%**；
若几乎每天都被对方准确提起（每天 +1 计数），约 8 天即可晋升，
存活率 = 0.8^8 ≈ **17%**——比阈值 30 时代快了约一个数量级，
珍贵回忆有望在数周内开始沉淀。仍嫌慢就把阈值继续降到 10~12。

## 四、长期记忆：数据文件

位置：`personas/<slug>/memory.json`（换人设只换目录，引擎通用）。

```json
{
  "schema": 1,
  "params": { "…见上…" },
  "meta": {
    "last_forget_date": "2026-10-29",
    "last_summary_date": "2026-10-29",
    "mention_bonus": { "date": "2026-10-29", "counts": { "a1b2c3d4": 1 } }
  },
  "ordinary": [
    { "id": "a1b2c3d4", "text": "…≤128B…", "count": 5, "created": "2026-10-28T16:00:00" }
  ],
  "precious": [
    { "id": "e5f6a7b8", "text": "…", "count": 15, "promoted": "2026-10-30T09:00:00" }
  ],
  "people": {
    "123456789": { "name": "某人", "labels": ["熟客"], "favor": 3 }
  }
}
```

> `meta` 由引擎自动维护：`last_forget_date` 防同日重复遗忘；`mention_bonus`
> 是提及加分的每日限次记录（跨重启持久化，刷不了分）。时间一律来自
> 时间源（事件时间 → 联网北京时间），与本地时钟无关。

实现：`memory/memory.py`（`MemoryStore`），纯标准库、无依赖。
生命周期钩子：`session_start()` / `session_end(texts)` / `mark_mentioned(ids)` /
`update_person(...)` / `format_for_prompt()`。

## 五、长期记忆：下机总结提示词模板（给聊天大脑的 LLM）

```
以下是本次聊天（自上机到下机）的完整记录。请以 {display_name} 的视角，
回顾这段相处，选出对你来说最重要、最值得记住的事情。

要求：
1. 最多 10 条，每条不超过 128 字节（约 42 个汉字），一句话写清一件事；
2. 只记"以后再聊起会想起来的"事实与感受，不记寒暄与日常琐碎；
3. 若你注意到某个具体的人对你特别重要或让你在意，
   在输出末尾单独给出"人物档案更新"，格式：
   人物更新 | QQ号 | 称呼 | 加标签:xx,xx | 减标签:xx | 好感度变化:+1/-2
   （没有变化就省略这一行）

输出格式（纯文本，每行一条）：
- 回忆内容一
- 回忆内容二
……
人物更新 | ……
```

## 七、长期记忆：调参指南

| 参数 | 效果 | 调大 | 调小 |
|---|---|---|---|
| `per_session_max_new` | 每会话写入上限 | 记忆更密集 | 记忆更稀疏 |
| `max_memory_bytes` | 单条长度上限（128B≈42 汉字） | 更具体 | 更凝练 |
| `ordinary_forget_rate` | 普通回忆遗忘速度 | 忘得快、稳态少 | 忘得慢、稳态多 |
| `precious_threshold` | 晋升难度（**最影响珍贵增长速度**） | 更稀有 | 更快沉淀 |
| `precious_forget_rate` | 珍贵层遗忘速度 | 珍贵层更小 | 珍贵层更大 |
| `mention_bonus_per_day` | 被提起的奖励（每天每条限 1 次，跨重启持久化） | 越被提及越难忘 | 更依赖时间 |

调参只需编辑 `personas/<slug>/memory.json` 的 `params`，引擎与数据格式不变。

## 八、短期记忆：滑动窗口 + 压缩摘要

解决"一次聊天聊到几百轮，上下文塞不下"的问题，模拟注意力的远近梯度：

```
┌─────────────────────────────────────────────────────────────┐
│  二级摘要（较早）   一级摘要（近期）      滑动窗口（最近 12 轮） │
│  最旧，最模糊   ←   较旧，较粗    ←   最新，逐字保留（可引用）  │
└─────────────────────────────────────────────────────────────┘
   滚动方向：窗口溢出 → 压缩成一级摘要 → 一级积满 → 压缩成二级 →
             二级超限 → 最旧两条合并（只降保真度，不丢信息）
```

| 参数 | 含义 | 默认 |
|---|---|---|
| `window_turns` | 滑动窗口保留的原文轮数 | 12 |
| `summary_chunk_turns` | 滚出窗口的对话每 N 轮压成一条一级摘要 | 10 |
| `max_level1_summaries` | 一级摘要上限，超出滚动压成二级 | 5 |
| `level2_chunk_summaries` | 几条一级摘要压成一条二级摘要 | 4 |
| `max_level2_summaries` | 二级摘要上限，超出时最旧两条合并 | 3 |
| `summary_max_chars` | 单条摘要的字符硬上限 | 300 |
| `context_budget_chars` | 注入 system prompt 的总预算 | 4000 |

实现：`memory/short_term.py`（`ShortTermMemory`）。
接口：`add_turn(role, name, text, channel)`（每条消息都调）、
`context_for_prompt()`（拼进 system prompt）、
`flush()`（下机收尾）、`save()/load()`（崩溃恢复）。
压缩由 `compress_fn` 回调（LLM）完成，失败自动退化为文本拼接。

**两条使用红线**：
1. 压缩 LLM 调用是同步发生在消息处理路径上的（每 10 轮多一次 2~5 秒延迟），
   当前简单可靠优先；将来嫌卡再改后台异步压缩。
2. **下机时的长期总结必须基于完整原始聊天日志**（机器人应单独留存
   `session.log`），不能只用短期记忆的摘要——摘要有损，会让长期记忆失真。
